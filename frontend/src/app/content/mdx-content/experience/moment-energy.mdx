## Core Contributions

### Telemetry Dashboard Query Optimization

**Impact:** API response times fell by approximately **70%** overall, including on the 1-2 hour windows most often viewed on graphs. Short queries of around 5 minutes improved slightly, while gains grew from hours to weeks. Long-running queries dropped from several minutes to seconds, and supported ranges expanded from days to weeks.

**Problem:** Querying historical battery telemetry became increasingly expensive as the requested time range grew. The legacy Express backend retrieved large volumes of sensor readings and performed additional aggregation and transformation in application code, resulting in **extremely long API response times**, **limited practical query ranges** due to http timeouts, and **poor user experience**.

As part of our architecture overhaul, I contributed to the Telemetry Service. I diagnosed, then rebuilt the telemetry pipeline across Athena, the API, and the React dashboard:

| Stage | Before | After |
| --- | --- | --- |
| Athena | Returned relatively raw readings | Filtered, downsampled, and aggregated readings, including rack, module, and cell-level calculations |
| EC2-hosted backend | Grouped readings, calculated measurement extremes, and assembled responses | Assembled responses from structured results using `Set` and `Map` lookups |
| API transfer | Uncompressed responses | Gzip compression in NestJS |
| React dashboard | Performed additional chart transformations | Consumed data already shaped for visualization |

#### Selective Telemetry Downsampling

Longer query ranges returned far more readings than a chart could visibly distinguish. The goal was to return only the resolution the graph could show, while retaining the key data points. I adjusted sampling resolution to the requested range, and anomaly flags kept the short-lived readings that regular sampling would drop. Our queries also filtered on partition keys so Athena could skip irrelevant S3 partitions.

Readings generally arrived every 10 seconds, but irregular timing, gaps, and restarts meant they did not always align with sampling targets. I grouped readings into time buckets and selected each sensor’s reading closest to the target timestamp.

The query followed these stages, using Athena/Presto CTEs:

```text
Read telemetry for the selected pack and time range
Assign each reading to a time bucket

For each sensor in each bucket:
    Keep the reading closest to the target timestamp

For each pack in each bucket:
    Calculate minimum and maximum voltage
    and maximum temperature across the selected readings
    Calculate the same extremes across all readings in the bucket

Return structured results for the dashboard
```

This reduced the records the backend and dashboard had to process, but brief spikes or anomalies between selected readings could be missed as plotted points. Bucket-wide minimums and maximums kept their magnitude, but not the exact reading or timestamp.

### Detecting and Flagging Telemetry Anomalies

**Impact:** The anomaly detector was deployed to production, flagging glitches and spikes from live telemetry and keeping those readings visible in long-range, downsampled charts.

Battery telemetry could contain brief glitches and spikes. I needed to flag these anomalies as readings arrived and retain their timestamps for later investigation.

To avoid repeatedly querying historical telemetry, I explored online algorithms, which update compact running statistics with each incoming reading.

I used the live MQTT telemetry stream to track a running **exponential moving average** (EMA), identifying readings that departed significantly from a device/sensor's recent behavior. This preserved the first detected reading's timestamp.


These flags covered what downsampling missed: readings selected five minutes apart might barely differ even though a sharp spike occurred between them.


We stored the timestamps identified by the live anomaly detector. When a long-range query covered those timestamps, we included their readings alongside the downsampled data regardless of whether regular sampling would select them.

#### Why I chose EMA

The detector needed a baseline that reflected each sensor's recent behavior. A cumulative approach like Welford's running variance weights every reading since startup equally, so old operating conditions keep shaping what counts as normal. EMA gives recent readings more weight and stores only a compact running value per sensor:

```text
ema_t = alpha * x_t + (1 - alpha) * ema_previous
```

Here, `x_t` is the incoming reading and `alpha` is a smoothing factor between 0 and 1. A larger `alpha` adapts faster; a smaller one produces a steadier baseline.

The tradeoff was responsiveness: a baseline that adapts too quickly can follow an anomaly, while one that adapts too slowly can lag behind a legitimate change in operation.

### Cloud Fault Detection System

**Impact:** The fault detection feature was deployed to production, automatically generating fault events from live telemetry and surfacing them through dashboard alerts and AWS SES email notifications.

The system consumed live measurements from AWS IoT Core MQTT topics and evaluated them against configurable thresholds retrieved from backend services.

**My implementation work included:**

- Building NestJS monitoring services to consume MQTT telemetry and evaluate threshold-based fault conditions.
- Caching threshold configurations to reduce repeated database lookups during telemetry processing.
- Implementing Athena-backed fault retrieval APIs and supporting historical investigation through Parquet-based data warehousing.
- Integrating fault detection with frontend dashboard alerts and email notifications through AWS SES.

#### Sensor Hysteresis and Fault Recovery

I also worked on hysteresis for transitions between fault severity levels. Separate trigger and recovery thresholds kept small sensor fluctuations from repeatedly triggering and clearing faults. For example, a reading could trigger a severe high fault above its upper threshold, then clear that state only after falling below its recovery threshold. If the high-warning condition still applied, the sensor would step back down to a warning rather than immediately returning to normal.

## Reflection

This work taught me to evaluate performance and information loss together. Faster charts still needed to retain evidence of short-lived anomalies. Comparing cumulative statistics with EMA helped me connect an algorithm's treatment of history to a product requirement: surfacing the readings downsampling would otherwise drop, even across longer time ranges.
